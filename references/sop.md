# 跨多年每日所在地点梳理 · 通用操作规范（SOP）

> 适用范围：你有多年的支付账单（微信/支付宝/云闪付，或海外银行/信用卡月结单），想还原
> 「**每一年、每一天的我大概在哪个城市**」。最终产物是一张覆盖全部日期的「每日城市表」+ 配套汇总，
> 可用于旅行回忆、报销/税务佐证、居住地证明、个人时间线归档。
> 本文档已把个人数据全部抽象成「示例」，任何地区、任何人照着做都能梳理自己的行程。

---

## 0. 这份规范能帮你做什么

- **输入**：几年的支付账单 + 你自己的机票/火车票/酒店/门票订单 + （强烈建议）带 GPS 的照片/视频。
- **输出**：
  - `每日所在城市_最终整合版.xlsx`（5+ 表：每日城市 / 停留段 / 城市汇总 / 飞机出行明细 / 火车出行明细）
  - `每日所在城市_逐日明细.csv`（方便按年、按城市筛选）
- **核心价值**：账单里的「消费地」不等于「你人在哪」。本文档教你怎么把一堆噪声账单，还原成可信的逐日地理轨迹。

---

## 1. 核心思路（30 秒看懂）

**数据流（8 阶段）：**

```
多源记录(支付 / 出行订单 / 导航打卡 / OTA核销 / 照片EXIF GPS)
   → ① 合并 + 字段标准化(城市归一)
   → ② 消费地逐日梳理(梳理版,含L0地标)
   → ③ 出行腿结构化(飞机/火车/大巴/自驾 → travel_legs.json)
   → ④ 实地证据提取(酒店/门票/线下核销)
   → ⑤ 照片 EXIF GPS 判定(账单缺失时段的主力)
   → ⑥ 每日城市推算(时间感知引擎) + 多轮纠错
   → ⑦ 产出(最终整合版 + CSV) → ⑧ 校验迭代
```

**证据等级（越往上越硬）：**

| 等级 | 来源 | 含义 |
|------|------|------|
| **L0 最硬** | **照片/视频 EXIF GPS**、导航/打车/打卡的 GPS 轨迹（高德/滴滴，或 Google Maps Timeline/Uber） | 直接证明「你那一刻物理上在这」，比任何消费都硬 |
| **L0 最硬** | 出行腿（飞机/火车/大巴）的**出发日/到达日**、**酒店/门票/线下核销** | 你那天一定在出发/到达城市或消费场所 |
| **硬证据** | 实地消费（酒店/门票/到店团购，及 OTA 线上买线下用） | 订酒店=必去住，订门票=必去玩，与出行腿**同权重** |
| **弱证据** | 普通线上/线下消费地点 | 只能作为线索，**不能单独定城市** |
| **兜底** | 邻日推算 / 行程连续填充 | 数据缺失时用，必须有安全闸保护 |

**三条最关键认知（贯穿全文）：**

> **① 支付地点 ≠ 你本人在哪。** 商户注册地/总部、商品产地、连锁门店分支地、线上商户都会把错误城市塞进账单。
> 国内典型：订票商户注册在天津但你从没去过天津；海外典型：Uber 账单显示 San Francisco 总部而人在 London。
> 所有「城市」都必须经过证据校验。
>
> **② GPS 类证据比消费更硬。** 照片 EXIF GPS、导航/打车轨迹直接锚定物理位置，作为 L0 优先采信。
>
> **③ 判定要「时间感知」。** 一天可能跨多个城市（早晨在 A 出发、傍晚到 B）。有效的判定是：
> **每日有效时段（07:00–24:00，排除睡眠段）内停留最久的城市为主城市，在途时间不计入任何城市。**
> 早期「到达优先」判定会把深夜到达误标整天，已被 v2.0 时间感知引擎替代。

## 2. 地区适配（先确认用户所在地区，其余流程完全一致）

核心方法论全球通用，仅「数据源」与「城市命名」按地区取用：

| 环节 | 中国大陆用户 | 海外用户 |
|------|------------|---------|
| 支付账单 | 微信/支付宝/云闪付导出 Excel | 银行/信用卡月结单 PDF→CSV（Chase/Amex/Wise/Revolut 等） |
| 出行票务 | 12306、航旅纵横/航司 App | 航司 App、Trainline/Amtrak/Eurostar/Rail Europe |
| 导航/打车 GPS | 高德/百度、滴滴/曹操、哈啰 | **Google Maps Timeline**、Uber/Lyft/Bolt/Grab 行程记录 |
| 实地订单 | 美团/携程/华住 | Booking/Agoda/Airbnb/酒店会员体系 |
| 照片 EXIF GPS | 相册照片（同一全球标准） | 相同（Photos/iCloud/Google Photos 导出均可） |
| 城市命名 | `省/市` 短格式（如 `新疆/阜康`） | `国家/城市`（如 `Thailand/Bangkok`），同两级结构 |
| 高频误判源 | 商户注册地、菜系名、商品产地 | 商户总部所在地、清关地、免税店注册地、**跨时区日期漂移** |
| 币种线索 | — | 账单币种突变（USD→THB）可辅助定位出境日 |

**海外特有注意事项：**
- **时区**：账单时间可能按发卡行时区或交易地时区记录，先确认口径；出行腿时刻用**当地时间**（出发写起飞地时间、到达写落地地时间）。
- **跨时区航班日期漂移**：红眼航班「22:00 出发、当地 05:00 到达但日历已 +1 天」——以到达地当地日历日为 `arr_date`。
- **城市归一化**：英文城市统一大小写与常用拼写（`St Petersburg` vs `Saint Petersburg`）；自由文本里的城市先做别名表（`Kowloon`→`Hong Kong/Hong Kong`）。
- **表达习惯**：与用户交流、表头命名跟随用户语言（中文用户中文表头，海外用户英文表头）。

## 3. 开工前准备

### 3.1 材料清单

| 类别 | 中国大陆 | 海外 | 用途 |
|------|---------|------|------|
| 支付类 | 微信/支付宝/云闪付账单 | 银行/信用卡月结单 | 主数据 |
| 出行订单 | 机票/火车票订单（12306/航旅/飞猪） | 航司订单、Trainline/Amtrak | 出行腿 |
| 导航/打车/打卡 | 高德/百度/滴滴/哈啰 | Google Timeline/Uber/Bolt | **L0 GPS 硬证据** |
| 实地订单 | 美团/点评/携程/华住 | Booking/Agoda/Airbnb | 实地证据 |
| **照片视频** | **手机/相机全部带 GPS 的照片视频** | 相同 | **L0，账单缺失时段主力** |
| 记忆类 | 相册、社交时间线、日记、工作地变迁 | 相同 | 校验与口述补腿 |

> 提示：多年数据建议**分段导出**（如每年一份）。照片 GPS 用 `exiftool` 批量提取（见 §7）。

### 3.2 先想清楚「个人常量」（写进配置文件，后面反复用）

- **`HOME_CITIES`（老家/长期居住地）**：消费层没证据时，默认归这里。
- **`WORK_BASE`（某年起的工作地）**：此后非工作地的异地城市都必须有真实出行腿佐证。
- **`TRANSIT_CITIES`（老家附近的中转站）**：只是出发/到达经此地，真实停留从不超 2 天。
- **`MAX_GAP`（行程连续填充阈值）**：默认 `14` 天。相邻两条腿空档 ≤ 此值且链不断时，中间天补为该城市。
- **特殊时期**：如疫情封城、服役、住院等长期滞留区间。
- **已知真实旅行段**：提前记下来，避免被误标。

### 3.3 环境

- Python 3.9+，安装 `openpyxl`（`pip install openpyxl`）
- `exiftool`（照片 GPS 提取用，[exiftool.org](https://exiftool.org) 单独安装）
- 一个**干净的工作目录**，把导出的账单和脚本都放进去
- 推荐：每次大改前 `cp xxx.xlsx xxx.xlsx.bak_日期` 备份（**先备份，再改**）

## 4. 阶段一：账单导出与合并（数据地基）

**目标**：把各平台账单合并成一张「合并明细表」，字段统一。

**做什么**：
1. 读入各份账单，对齐到统一字段（见附录 B）。海外用户：PDF 账单先转 CSV，字段映射到「时间/对方/商品(描述)/金额/城市」。
2. 逐行标注：`消费性质`（线上/线下/连锁/转账/理财…）；`判定层级`（能直接证明在当地的记 `L0`，其余留空）。
3. 去重：同一笔交易若多平台都出现，保留一笔。
4. 输出 `合并消费地梳理_{起始}-{结束}.xlsx`，工作表名 `合并明细(含消费地)`。

**坑**：
- 各平台字段名不同（微信叫「交易类型」、支付宝叫「交易分类」；Chase 叫 Description），先做字段映射表。
- 时间格式不一致，统一成 `YYYY-MM-DD HH:MM`；确认时区口径（海外账单尤其重要）。

**阶段成果**：字段统一、带标注的合并明细表。这是后面所有步骤的输入，**务必备份**。

---

## 5. 阶段二：字段标准化与城市名归一化

**目标**：让「同一个城市」在数据里只有一种写法，否则会拆成两行。

**做什么**（写两个归一化函数，全程复用）：
- 国内 `norm_prov(p)`：`广西壮族自治区→广西`、`新疆维吾尔自治区→新疆`（含「新疆维吾尔」半截写法）、`浙江省→浙江`、`北京市→北京`。
- 国内 `norm_cs(city)`：`浙江省/杭州市` → `浙江/杭州`；直辖市省=市，特殊处理成 `北京/北京`。
- 海外：统一 `国家/城市` 两级格式；英文大小写与拼写别名表（`Kowloon→Hong Kong/Hong Kong`、`Giza→Egypt/Giza`）。

**坑**：同一城市因写法不同被拆成两行 → 归一化后消除；半截写法 → 补映射表。

**阶段成果**：合并明细「省/市」字段统一为短格式。后续所有城市比较都基于这个格式。

## 6. 阶段三：消费地逐日梳理（梳理版）

**目标**：先不靠出行记录，单看每天消费，推断一个「候选城市」。

**做什么**：
1. 按日期分组，每天汇总当日消费指向的所有城市，写成 `当日全部城市`。
2. 主城市 = 当日最有把握的城市（线下到店、L0 地标优先）。
3. 输出 `每日所在城市_梳理.xlsx`。

**核心铁律（来自真实踩坑）：**
> **城市只从「商品/描述」字段提取，绝不从「交易对方/merchant」提取。**
> 「交易对方」是公司名，写的是**注册地/总部**而不是你所在城市。只有「商品」字段
> （如「XX酒店(杭州西湖店)」「Hilton Bangkok Sukhumvit」）才指向真实地点。

**坑**：公司注册地误判（剔除含「股份有限公司/科技有限公司/集团/商城/旗舰店/网店/Ltd/Inc/Corp」字样的）；消费层只能作为**弱证据**。

**阶段成果**：`梳理版.xlsx`。它一定不准，但它是后续整合的基线。

## 7. 阶段四：出行腿结构化（travel_legs.json）

**目标**：把机票/火车票变成机器可读的「出行腿」，这是**最硬的地理位置证据**。

**结构**（每条腿，完整字段定义见 `travel_legs_schema.md`）：
```json
{
  "type": "flight",          // flight / train / bus / drive / ship
  "dep_date": "2024-07-18",  // 出发日
  "arr_date": "2024-07-19",  // 到达日（跨夜则≠出发日）
  "dep_min": 600,            // 出发时间(分钟, 10:00=600)，当地时间，用于排序
  "arr_min": 1320,           // 到达时间(分钟)，当地时间
  "from": "浙江/杭州",
  "to":   "甘肃/兰州",
  "no":   "MUxxxx",
  "stops": [],               // 经停站(不下车游玩的)，记入到达日
  "status": "已使用",         // 或 "用户口述"
  "raw":  "2024-07-18 杭州→兰州 MUxxxx"
}
```

**长途跨日交通的每日记录规范（重点）**：
- **跨夜单程**：出发日标「出发城市」(`_dep`)，到达日标「到达城市」(`_arr`)；中间有整日则标为到达城市（在途）。
- **经停站**：途中停靠但不下车（如青藏铁路经停格尔木、那曲），用 `stops` 记入到达日，出现在「当日全部城市」但**不算停留段**。
- **多日长途在途**：在途整日**不要算作老家/锚点城市**；用 `MAX_GAP` 行程连续填充补为到达城市（配合安全闸）。
- **自驾跨多日**：靠**导航 App 每日定位/打卡点**或沿途照片 GPS 定每天城市；关键落脚城市当「虚拟出行腿」或 `onsite` 录入。
- **同日多段**：先飞后火车、火车接大巴，必须靠 `dep_min` 排序。
- **海外跨时区**：`dep_min/arr_min` 用当地时间；`arr_date` 以到达地当地日历日为准。

**坑**：
- **口述补腿**：记得但订单没了（朋友代订/现金票），`status` 标「用户口述」补进 legs，否则中间天会被误标成老家。
- **大环线缺腿**：只记头尾，中间城市没腿，会被消费层拽回老家。补中间关键腿 + 调大 `MAX_GAP`（但绝不无限顺延）。

**阶段成果**：`travel_legs.json`，覆盖全部有订单/有记忆的出行。这是最终整合的主干证据。

## 8. 阶段五：实地证据提取（酒店 / 门票 / 到店消费）

**目标**：把「酒店、门票、到店团购」升级为与飞机火车**同权重**的硬证据。

**规则**：订酒店 = 必去住；订门票 = 必去玩；到店团购 = 必去吃。这三类消费的地点与出行腿同级别，能覆盖「老家锚点」。

**做什么**：
1. 在合并明细里筛「酒店/民宿/门票/景区/到店餐饮」类记录。
2. **只从「商品」字段提城市**（同阶段三铁律）。
3. 排除干扰：酒店用品（=网购）、外卖/买菜、**菜系名误判**（「淄博烧烤」「Sichuan Cuisine」是风味不是城市）、公司注册名（含 Ltd/Inc/股份 等字样）。
4. 提取到的城市并入出行证据集（标记来源 `onsite`）。

**跨境场景**（如陆路口岸出入境）：口岸/关卡所在地是强实地信号；账单币种突变（USD→本地币）可辅助定位出境日。

**阶段成果**：实地证据集，与出行腿合并后参与最终判定。

## 9. 阶段六：照片 EXIF GPS 判定（账单缺失时段的主力）

**适用**：账单滞后/缺失的时段（如当年账单未出）、纯旅行期。详细方法与实战教训见 `photo_gps_method.md`。

**做什么**：
1. `exiftool` 批量提取照片/视频的 `DateTimeOriginal + GPSLatitude + GPSLongitude`：
   `exiftool -json -DateTimeOriginal -GPSLatitude -GPSLongitude -r 目录/ > photo_gps_raw.json`
2. 用 `scripts/photo_gps_judge.py` 反向地理编码（nearest_city）+ 时间感知聚合，产出每日 GPS 候选城市。
3. **三道保险（全部必做）**：
   - **距离审计**：照片点距匹配城市中心 > 0.3°（约 33km）→ 当日标 ⚠️ 需复核。防「城市库缺目的地」——实战教训：坐标库缺「阜康」，天池两天被错配到 40km 外省会；
   - **单点飞地检测**：当天仅 1-2 个 GPS 点且远离邻日 → 不可直接采信（可能是他人照片/水印定位）；
   - **时区口径**：EXIF 时间为拍摄设备本地时间，与票务口径一致；跨时区旅行按设备时区归日。
4. GPS 证据按 `L0` 并入每日证据集；与出行腿冲突时以出行腿到达/出发+GPS 共同核对。

**阶段成果**：每日 GPS 候选城市 + 距离/飞地警告清单（供人工复核）。

## 10. 阶段七：每日城市推算与整合（最终整合版）

**目标**：把 消费层 + 出行腿 + 实地证据 + 照片GPS 按优先级合成「每一天的主城市」。

**时间感知判定引擎（v2.0 核心）**：
- 每日**有效时段 07:00–24:00**（排除睡眠段 00:00–07:00），按出行腿时刻把一天切成片段；
- 每片段归属一个城市（到达时刻前算出发城市、到达后算到达城市；在途不计）；
- **有效时段内停留最久的城市 = 当日主城市**；跨夜全天在途归到达城市；
- `carry-in` 按当日首个事件本地判定：首个事件是出发 → 早晨在出发地；首个事件是到达 → 在途。
- `transit_leg` 跟踪：只接受当前在途腿的到达事件，过滤「陈旧到达」污染（实战：某日到达事件被前一天夜车腿误触发）。

**行程连续填充（gap-fill）双闸**：
- 相邻两条腿，若「前腿到达城市 == 后腿出发城市」（链不断）且空档 `1 <= gap <= MAX_GAP`，中间天补为该城市；
- **闸1**：中间天消费层已是「非老家真实城市」→ 保留不覆盖；**闸2**：当天有 L0 硬地标证明在别处 → 不覆盖；
- **链断**（缺回程腿）→ 不填充，回落消费层（防「到 A 后永居 A」式错误顺延）。

**中转城市约束**：老家附近中转站真实停留**从不超 2 天**；>2 天连续段只保留有出行腿/实地证据的当天，其余归老家。

**特殊时期覆盖**：封城/滞留等特殊时期整段强制归滞留地（记 ⚠️ 备注）。

**用户核实校正（最后一道关）**：导出初版 → 本人逐日核对 → `CORRECTIONS = {日期: 正确城市}` 显式覆盖；**清洗「当日全部城市」列**：只保留主城市 + 有真实出行腿/L0/实地证据的城市。

**阶段成果**：`每日所在城市_最终整合版.xlsx`（5+ 表）+ `每日所在城市_逐日明细.csv`。

## 11. 阶段八：校验与纠错迭代

**这是质量分水岭。** 初版一定有误，靠下面几招反复迭代：

**自查清单**：
- [ ] 每个城市「首次/末次出现」是否符合记忆？
- [ ] 停留段长度合理？（中转站 >2 天 → 可疑）
- [ ] 邻日是否连续？（今天 A、昨天 B、明天 A，没出行腿 → 必错）
- [ ] 距离审计/飞地警告日是否全部复核？
- [ ] 备注列（⚠️）是否暴露了冲突日？

**迭代方法**：
1. 导出 → 自己翻一遍 → 列问题清单（「X月X日怎么有个Y城，我没去过」）。
2. 判断根因：商户注册地？缺腿？中转城市？坐标库缺目的地？时区漂移？
3. 改对应配置/规则（加 legs、扩充 city_coords、调 MAX_GAP、补 CORRECTIONS、加安全闸）。
4. 重跑脚本（**重跑前先备份**），看报告「本次改了多少天」。
5. 重复直到你认可。模糊日期直接问用户，口述结果标 `[用户确认]` 写入备注。

## 附录 C：常见坑速查表（按出现频率排序）

| # | 坑 | 现象 | 解法 |
|---|----|------|------|
| 1 | **商户注册地/总部误当所在地** | 从没去过的城市出现 | 城市只从「商品」提；剔除公司名后缀词 |
| 2 | **商品产地/线上商户误当所在地** | 莫名城市出现 | 清洗「当日全部城市」，只留有出行腿/L0/实地证据的 |
| 3 | **菜系名误判城市** | 「淄博烧烤(深圳店)」标成淄博 | 排除菜系词当地点 |
| 4 | **省份后缀/拼写未归一** | 同城拆成两行 | `norm_prov`/`norm_cs`/别名表归一 |
| 5 | **小假期中间日回老家** | 2~3天出行中间天错 | gap-fill 双闸（链不断 + MAX_GAP） |
| 6 | **大环线/长途缺腿** | 中间天被标回老家 | 补中间腿；`MAX_GAP` 调大但不无限 |
| 7 | **链断后错误顺延** | 缺回程腿后天天都是 A 城 | 链断→回落消费层，不填充 |
| 8 | **中转城市当多日停留** | 中转站被标成多日 | 中转城市约束：>2天只留有证据当天 |
| 9 | **跨夜出行腿中间天漏标** | 夜车「在路上」的天没算 | 中间天标为到达城市 |
| 10 | **深夜到达污染整日** | 23:50 到达被算整天 | 时间感知引擎（有效时段 07:00–24:00） |
| 11 | **陈旧到达污染** | 前一天腿的到达事件误触发 | `transit_leg` 只认当前在途腿 |
| 12 | **城市反查库缺目的地** | GPS 被就近匹配到错误城市（天池→40km外省会） | 距离审计(>0.3°⚠️) + 扩充 city_coords |
| 13 | **单点飞地** | 孤立 GPS 点（他人照片/水印定位） | 飞地检测：1-2 点且远离邻日不采信 |
| 14 | **海外跨时区日期漂移** | 红眼航班到达日错一天 | 出行腿用当地时间、按到达地日历归日 |
| 15 | **L0 格式不匹配假冲突** | 归一前比较导致安全闸失效 | 全程用归一化短格式比较 |
